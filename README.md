## 任务一：Tally 选票业务本地实现 — 任务说明

> 适用场景：把线上 `xmyzstudent.com` 的「tally 选票（实时唱票）」业务，在本地用镜像前端 + 自建 Flask 后端完整复刻一遍。
> 本文档可直接作为任务提示词（Prompt）提交给 AI 编码助手，或作为团队任务规格（Spec）归档。

### 1. 项目背景

- **源仓库**：`https://gitee.com/mc_lhz/aitest-using-xmyzstudent/`
- **项目性质**：一个 **SPA 前端项目**，是基于 JS 路由表对线上站点 `xmyzstudent.com` 的**完整前端镜像**（即把源站的前端 HTML/CSS/JS 原样镜像到本地，路由表与源站一致）。
- **前置动作**：先**初步分析项目架构**，定位 tally 相关业务代码与路由。

### 2. 任务目标

在仓库内**新建 `tally/` 文件夹**，在其中开发一个**独立的 Flask 服务器**，本地完整实现「tally 选票（实时唱票）」业务。

### 3. 约束与要求

#### 1. 前端：复用镜像，禁止自研
- 直接**复制并复用**网站镜像中的 `html` / `css` / `js`，**不要自己编写**任何前端代码。
- 以源站前端为准，保证交互与线上一致。

#### 2. 后端：反推接口 + 单文件存储
- 根据网站镜像中 **tally 相关业务 JS 的实现**，**反推其接口契约**（请求路径、方法、出入参），编写**完整的 Flask 后端**。
- 使用**单个 `tally.json` 文件**存储全部活动信息（活动、候选人、票数、操作记录等）。

#### 3. 后端需完整实现三大模块
后端必须覆盖以下三块前端所对应的业务，且**大屏必须使用原网站所用的 WebSocket**：
- **活动管理页**：活动的增删改查、状态切换、列表展示。
- **唱票控制台**：现场录票、撤销、操作日志等。
- **大屏**：实时展示唱票结果，**必须连接源站所使用的同构 WS 地址**（大屏实时刷新靠 WebSocket 推送）。

#### 4. 静态文件：最小化复制
- 复制静态文件时，**仅复制与本业务相关的文件**，**不要复制整站所有文件**。
- 目标是「tally 业务专用的最小前端子集」。

#### 5. 路由规范：与源站同构
- 路由规范与源站**保持一致**，**不需要带 `XMYZStudent` 前缀**。
- 如有 API 相关路由，也**直接拼接在根路由后面**（例如 `/api/v2/...`、`/tally/screen/:id`）。

#### 6. 初始数据：抓取线上四次历史活动
- 源站已有**四次活动**（id 分别为 `1`、`2`、`3`、`4`）。
- 需要**请求 `xmyzstudent.com` 并分析其 JS 代码**，抓取这四次活动的 JSON 数据，写入 `tally.json` 作为**初始数据**。
- **注意**：抓取过程**不需要认证**，若401，请**自行分析原因**。

### 4. 收尾：前端代码治理

完成上述功能后，需对复制过来的 JS 代码进行治理：
- **语义化**变量与函数命名；
- **格式化**代码（统一缩进、换行）；
- 添加**详尽注释**，说明业务含义与接口对应关系。

> 注：源站前端是构建产物（压缩/混淆），治理以「可读化 + 注释」为目标，不改写其渲染逻辑。

### 5. 最终交付物

1. **可运行的本地 Flask 服务**（`tally/` 目录），含前端静态子集与 `tally.json` 初始数据。
2. 一份**《源站 tally 业务完整实现链路分析报告》**，覆盖：
   - 业务画像、前端依赖关系、接口契约、端到端时序、状态机、数据模型。
3. 以本案例为素材，向读者**讲解 WebSocket 前端与后端的相关知识**（升级握手、帧、广播模型、前端重连、心跳等）。

### 6. 验收标准（建议）

- [ ] `tally/` 独立可启动，前端复用镜像文件、非自研。
- [ ] 后端 12 个 REST 接口 + 1 个 WS 地址与源站逐字对应。
- [ ] 活动管理页 / 唱票控制台 / 大屏三块功能完整可用。
- [ ] 大屏经 WebSocket 实时刷新，且 WS 地址与源站同构。
- [ ] 静态文件仅为 tally 相关业务子集（非整站）。
- [ ] `tally.json` 含源站 id=1/2/3/4 四次活动真实初始数据。
- [ ] JS 已语义化、格式化、加注释。
- [ ] 链路分析报告 + WebSocket 教学文档齐备。

## 任务二：Ticket 票务业务（抢票 / 审票 / 核销）本地实现 — 任务说明

> 适用场景：把线上 `xmyzstudent.com` 的「ticket 票务（活动抢票 → 后台审核 → 现场核销）」业务，在本地用镜像前端 + 自建 Flask 后端完整复刻一遍。
> 本文档可直接作为任务提示词（Prompt）提交给 AI 编码助手，或作为团队任务规格（Spec）归档。
> **本任务不涉及 WebSocket**——经核实，源站票务业务全部为请求-响应式交互。

### 1. 项目背景

- **源仓库**：`https://gitee.com/mc_lhz/aitest-using-xmyzstudent/`
- **项目性质**：一个 **SPA 前端项目**，是基于 JS 路由表对线上站点 `xmyzstudent.com` 的**完整前端镜像**（即把源站的前端 HTML/CSS/JS 原样镜像到本地，路由表与源站一致）。
- **前置动作**：先**初步分析项目架构**，定位 ticket 相关业务代码与路由。本业务涉及 **7 个页面**（用户侧 3 个 + 后台 4 个）与 **1 个 API 封装 chunk**。

### 2. 任务目标

在仓库内**新建 `ticket/` 文件夹**，在其中开发一个**独立的 Flask 服务器**，本地完整实现「ticket 票务」业务。

### 3. 约束与要求

#### 1. 前端：复用镜像，禁止自研

- 直接**复制并复用**网站镜像中的 `html` / `css` / `js`，**不要自己编写**任何前端代码。
- 以源站前端为准，保证交互与线上一致。
- 仓库中 `assets/ticket-*.js` 已是**部分语义化**产物（API 函数已具名），可作为主要线索。

#### 2. 后端：反推接口 + 单文件存储

- 根据网站镜像中 **ticket 相关业务 JS 的实现**，**反推其接口契约**（请求路径、方法、出入参），编写**完整的 Flask 后端**。
- 使用**单个 `ticket.json` 文件**存储全部数据（活动、场次/档期、票据、审核备注、核销记录等）。
- **注意**：源站所有 JSON 接口的响应信封统一为 `{ "code": ..., "data": ..., "message": ... }`，且 **HTTP 状态码与业务成败是两回事**（HTTP 200 也可能 `code` 非 200，前端只认 `code`）。请自行从镜像 JS 中确认细节并严格对齐。

#### 3. 后端需完整实现四大模块

后端必须覆盖以下 7 个前端页面所对应的全部业务：

- **用户侧 · 活动抢票列表**（`/ticket`）：分页、状态筛选、加载更多。
- **用户侧 · 活动详情与抢票**（`/ticket/:id`）：场次列表、倒计时、附加信息表单、抢票提交、抢票成功弹窗。
- **用户侧 · 我的票据**（`/ticket/my`）：按状态分组展示、票码复制、跳回活动详情。
- **后台 · 票务管理与活动编辑**（`/admin/tickets`、`/admin/tickets/new`、`/admin/tickets/:id`）：活动增删改查、状态切换、**档期（场次）增删改**、统计卡片、封面上传。
- **后台 · 审票管理**（`/admin/tickets/:id/review`）：按状态/档期筛选、单条审核、批量审核（通过/驳回）、按档期下拉（仅多档期时出现）。
- **后台 · 验票核销**（`/admin/tickets/verify`）：按票码查询票据全信息 + 附加信息，确认核销。
- **后台 · 票据导出**：导出为 `.xlsx` 文件，需正确设置 `Content-Disposition`（含 `filename*=UTF-8''...`，以支持中文文件名），并支持按状态、按档期过滤。

#### 4. 必须解决的前端 `baseURL` 硬编码问题

- 镜像的入口 chunk 中，axios 实例的 `baseURL` 是**指向线上域名的绝对地址**，且票据导出接口**不走 axios**、自行拼接绝对 URL 请求。
- 若不处理，本地服务将**完全收不到任何请求**。
- 请自行分析并解决（改写该地址 / 反向代理 / 其他方案均可），并在交付文档中说明你采用的方式与理由。

#### 5. 抢票一致性（核心考察点）

- 抢票接口必须**原子地**完成：「校验场次可抢 → 每场次去重 → 每用户每活动限额 → 库存扣减 → 生成票据与票码 → 落盘」这一整串动作。
- 在**单文件 JSON 存储**的前提下，你需要自行设计并发控制方案（进程内锁 / 文件锁 / 原子替换写 / 乐观锁版本号等均可），并保证：
  - **不超卖**：并发抢票时售出总数不得超过 `totalTickets`。
  - **不重复**：同一用户对同一场次不可重复持有；`max_tickets_per_user` 为**每用户每活动**的累计限额（跨场次生效），默认值 1。
  - **票码唯一**：票码为**固定 5 位**（前端按 5 位校验并做大写归一），需保证全局唯一且不与已有票码碰撞。
  - **核销幂等**：同一票码二次核销**不得**产生第二次扣减或把状态改坏（前端靠响应中的成功标志区分，而非 HTTP 错误）。
- **注意**：前端只做「预检」，存在 TOCTOU 窗口（多标签页 / 多设备可绕过），**所有强一致校验必须由后端兜底**。
- **注意**：源站前端把「审核驳回」的落地状态设计成了**已取消**而非「已拒绝」，且该状态**不占用用户限额、允许重新抢票**。请自行核实这一设计并在后端一致实现。

#### 6. 静态文件：最小化复制

- 复制静态文件时，**仅复制与本业务相关的文件**，**不要复制整站所有文件**。
- 目标是「ticket 业务专用的最小前端子集」，共 **24 个 assets 文件**，合计约 **719 KB**（7 个页面 chunk 及其 CSS、1 个 API chunk、1 个上传组件 chunk、3 组公共组件及其 CSS、以及入口 chunk 自身与其全局 CSS）；另需仓库根的 `index.html` 与 `vite.svg`。
- **注意**：镜像里存在与本业务**无关**的 chunk（如辩论赛/大屏业务的模块文件），不要一并复制——只复制票务路由真正会加载的那些。
- **注意**：入口 chunk 引用了全站 72 条路由的懒加载清单，虽然只有票务路由会被实际访问，但你**不可裁剪入口 chunk 本身**。

#### 7. 路由规范：与源站同构

- 路由规范与源站**保持一致**，**不需要带 `XMYZStudent` 前缀**。
- 如有 API 相关路由，也**直接拼接在根路由后面**（例如 `/api/v2/ticket-activities`、`/api/v2/admin/ticket/...`）。
- 前端为 SPA，**非静态文件的深路由需要回落到 `index.html`**，否则刷新 `/ticket/88` 等页面会 404。

#### 8. 鉴权与权限

- **本任务不要求实现登录注册**，请复用仓库内部脚本解锁登录态（见开头「注意」第三条）。
- 但后端仍需正确处理鉴权：请求头为 `Authorization: Bearer <token>`；**token 缺失或无效时须返回真正的 HTTP 401**（前端监听 401 事件来触发登出，返回 200 + 业务码不会生效）。
- 后台接口需校验权限位 `ticket.manage`（由 `/permissions/my` 下发）。源站对无权限请求返回 **HTTP 403 + `{code:403, message:"权限不足"}`**，请对齐这一行为。

#### 9. 初始数据：抓取线上真实数据

- 需要**请求源站 `xmyzstudent.com` 并分析其 JS 代码**，抓取真实活动的 JSON 数据，写入 `ticket.json` 作为**初始数据**。
- 抓取所需凭据（**出题方提供的公共测试账号，请勿提交到任何公共位置**）：

  | 字段 | 值 |
  |---|---|
  | 接口基址 | `https://api.xmyzstudent.com/api/v2` |
  | 登录接口 | `POST /auth/login`，体为 `{"loginType":"normal","username":"...","password":"..."}` |
  | 用户名 | `AITest` |
  | 密码 | `123456` |
  | 请求头 | `Authorization: Bearer <登录响应 data.token>` |
  | Token 有效期 | 登录响应中的 `expiresAt`（秒级时间戳） |

  > **说明**：上表凭据为出题方**主动发放**的公共测试账号，属于任务输入的一部分，**豁免**下方第 11 条验收项。但你仍需注意：**不得把你自行登录后拿到的真实 token 写进任何交付文件**（包括分析报告与教学文档），报告中一律以 `<token>` 占位。

- 源站**当前共有 18 个活动**（`status=all`），含 `active` 5 个、`ended` 12 个、`cancelled` 1 个；不带 `status` 参数的默认列表只返回 `active` 那 5 个。
- **重要**：该账号是**普通用户，不具备 `ticket.manage` 权限**。因此：
  - 用户侧接口（活动列表/详情、我的票据）**可以抓到真实数据**；
  - **全部 15 个 `/admin/ticket/**` 后台 REST 接口与导出接口（共 16 个）都会返回 HTTP 403「权限不足」，抓不到真实数据**。
  - 请自行验证上述现象，并据此**自造后台侧的初始数据**（活动、档期、票据、审核与核销记录），且必须**覆盖状态机全集**：
    - 活动状态：`draft` / `published` / `active` / `ended` / `cancelled`；
    - 票据状态：待审核 / 已确认 / 已使用 / 已取消；
    - 配置组合：需审核、免审核、需绑定校园网、需填附加信息（多个必填字段）、每人限多张。
- **注意**：源站返回的部分字段是**前端并不消费**的（例如场次上的活动标记、活动配置里的年级白名单），但既然源站返回了，本地实现也应如实返回；这类字段请自行发现并记录。
