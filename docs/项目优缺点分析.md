# Tally 双项目优缺点分析

> 对比对象
> - **L 项目** = `XMYZStudent/tally`（本次任务产出，最小裁剪版）
> - **D 项目** = `Desktop/httpsxmyzstudent.com/flask-tally`（整站镜像 + 补后端版）
>
> 结论先行：两个项目都能在本地跑通 tally 业务（前端都正确指向本地 Flask，12 REST + WS 路径与源站逐字一致）。差异不在"能不能用"，而在"工程化程度"和"镜像策略"。

---

## 0. 一句话总评

- **L 项目**：严格贴合任务 6 条约束的「最小可用 tally 专用服务」——干净、可控、可审计、可测，但牺牲了整站可浏览性。
- **D 项目**：「整站克隆壳 + 先补 tally 后端」——视觉上最接近源站全貌，但后端工程化弱、数据模型不兼容、`seed.py` 已不可用。

---

## 1. L 项目（本次产出）优点

| # | 优点 | 体现 |
|---|------|------|
| 1 | **严格满足任务约束** | 仅复制 18 个 tally 相关静态文件（757K），未复制整站；路由表从 91 条裁到 4 条 + 兜底，未知路由回落管理页 |
| 2 | **有鉴权开关** | `authToken` 支持环境变量 / `--token` 注入；设了就严格比对 `Authorization: Bearer`，不过返回 401（与源站 body 结构一致） |
| 3 | **票数有下限保护** | `max(0, voteCount + delta)`，杜绝误投导致负票 |
| 4 | **不可变撤销审计** | 撤销不删除/改写原记录，而是标记 `undone=True`，保留完整操作链（合规友好） |
| 5 | **线程安全的 WS 模型** | 每个连接一个 `Queue`，`rooms = {activityId: set(Queue)}`，广播经队列转发，规避 simple-websocket 收发状态机非线程安全的问题 |
| 6 | **原子落盘** | 先写 `.tmp` 再 `os.replace` 覆盖，进程崩溃不会留半截 JSON |
| 7 | **可观测 / 可测** | 自带 `/api/v2/tally/_debug` 端点；`_e2e.mjs` 20 项断言（REST + WS 广播 + 撤销回滚）全过 |
| 8 | **代码可读** | `useTallySocket.js` 语义化重写 + 详尽注释；4 个页面 chunk 注入变量映射注释；主 bundle 裁剪处留中文说明 |
| 9 | **文档完整** | `README.md` + `链路分析报告.md` + 本对比/优缺点文档，覆盖运行、路由、移植改动、WS 教学 |

## 2. L 项目（本次产出）缺点

| # | 缺点 | 说明 |
|---|------|------|
| 1 | **丢失整站浏览体验** | 只保留 4 条 tally 路由，访问源站其它栏目（新闻、公示等）会全部回落到管理页，看不到原站全貌 |
| 2 | **依赖本地 token 注入才安全** | 默认 `authToken=None` 时是"本地放行"模式；真要防未授权改票，必须手动设 token（源站账号体系未移植） |
| 3 | **初始数据需手动复位** | `tally.json` 为干净初态，4 次历史活动虽抓取过但需另行灌入才能复现线上快照 |
| 4 | **前端仍是编译产物** | 页面 chunk 是 Vue 编译后的压缩代码，加注释只是"可读化"而非"可维护化"，改业务逻辑成本高 |

---

## 3. D 项目（Desktop）优点

| # | 优点 | 体现 |
|---|------|------|
| 1 | **镜像广度最大** | 170 个静态文件 / 3.9M / 91 条路由，整站壳完整，非 tally 页面也能渲染（视觉最接近源站） |
| 2 | **上手零配置** | 无鉴权、无 token，启动即全功能，适合"先跑起来看看"的演示 |
| 3 | **数据模型贴近源站直觉** | `records` 为顶层扁平数组（带 `activityId`/`candidateId`），与多数"操作日志表"设计一致，易对接外部系统 |
| 4 | **WS 实现直观** | `_ws_clients = {activity_id: set(ws)}` 直接 `ws.send`，代码量小、易读懂（单连接低并发场景够用） |
| 5 | **默认端口 5000** | 与 Flask 惯例一致，免记端口 |

## 4. D 项目（Desktop）缺点

| # | 缺点 | 风险 |
|---|------|------|
| 1 | **无鉴权** | 任何能访问服务的人都能改票 / 删活动，现场公网暴露（如经隧道）即裸奔 |
| 2 | **票数可成负数** | vote 接口无 `max(0)` 下限，撤销超过已投数会扣成负票，大屏显示异常 |
| 3 | **撤销可篡改历史** | 撤销原地改 `type` 字段（非不可变标记），操作审计链不完整，事后无法追溯"谁何时撤了哪一票" |
| 4 | **WS 非线程安全** | 多个连接并发 `ws.send` 时，simple-websocket 的收发状态机在多线程下可能竞态（高并发唱票现场有隐患） |
| 5 | **落盘非原子** | `save_data` 直接覆盖写，进程在写中途崩溃会留下损坏的 `tally.json` |
| 6 | **`seed.py` 已不可用** | 依赖的 `raw_ws_1..4.json` 输入文件缺失，直接运行即 `FileNotFoundError`；数据实际是写死在 `tally.json` 里的 |
| 7 | **体积大、冗余多** | 3.9M 静态资产里绝大部分 tally 用不到，部署 / 传输成本高 |
| 8 | **数据模型与 L 不兼容** | 顶层 `records` vs 活动内嵌 `records`，两者 `tally.json` 不能直接互换，需迁移脚本 |
| 9 | **缺测试与文档** | 无 e2e、无 README、无链路分析，后续维护靠读源码 |

## 5. 关键维度对照表

| 维度 | L 项目 | D 项目 | 胜出 |
|------|--------|--------|------|
| 镜像范围 | 18 文件 / 4 路由 | 170 文件 / 91 路由 | D（广度） |
| 安全（鉴权） | ✅ 开关 + 401 | ❌ 无 | **L** |
| 数据完整性 | ✅ 不可变审计 | ❌ 原地改 type | **L** |
| 票数下限 | ✅ max(0) | ❌ 可负 | **L** |
| WS 并发安全 | ✅ Queue 模型 | ❌ 直连 send | **L** |
| 落盘安全 | ✅ 原子替换 | ❌ 直接覆盖 | **L** |
| 可测性 | ✅ 20 项 e2e | ❌ 无 | **L** |
| 可复现（seed） | ✅ 数据内置 | ❌ seed 缺输入 | **L** |
| 文档 | ✅ 3 份 | ❌ 无 | **L** |
| 代码体积 | ✅ 757K | ❌ 3.9M | **L** |
| 整站浏览体验 | ❌ 仅 tally | ✅ 全站壳 | D |
| 上手零配置 | ❌ 需设 token 才安全 | ✅ 启动即用 | D |

## 6. 选型建议

- **用 L 项目**，当：要交付一个可控、可审计、能公网安全暴露的唱票服务；要满足"仅复制相关业务文件"的约束；要长期维护。
- **用 D 项目**，当：只是想本地快速看一眼源站全貌（含非 tally 页面）；做演示原型、不计较安全与并发；或需要整站壳作为其他业务的脚手架。
- **若两者要共用数据**：必须写迁移脚本——D 的顶层 `records` → L 的活动内嵌 `records` 并补 `undone` 字段，反之亦然。不能直接拷贝 `tally.json`。
- **推荐演进**：以 L 为基线，若需要整站浏览，再按需把 D 的非 tally 静态资产按路由补回（而非整站照搬），兼顾安全与广度。
